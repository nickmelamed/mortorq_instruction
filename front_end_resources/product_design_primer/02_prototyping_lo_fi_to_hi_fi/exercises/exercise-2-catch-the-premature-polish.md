# Exercise 2: Catch Premature Polish (Break This on Purpose)

## Goal
See directly how a bad structural decision hides once it's dressed up, compared to when it's still just boxes and arrows.

## Steps
1. Take your wireframe from Exercise 1 (or any wireframe) and apply quick, rough visual polish to it — pick any colors and fonts you like, spend real effort making it look finished. Don't fix any structural issues while you do this, even ones you already know about.
2. Show the polished version to someone new (who hasn't seen the plain wireframe) and ask them to critique it.
3. Separately, show the plain, unstyled wireframe version of the same screen to a different person and ask them to critique it.
4. Compare the two sets of feedback. Which version got comments about layout and structure, and which got comments about color and style choices instead?
5. Note whether either reviewer pointed out a structural problem you already knew was there.

## Self-Check
- [ ] I compared feedback on a polished version against feedback on a plain wireframe of the same screen
- [ ] I can describe a specific structural issue that got mentioned in one review and missed (or reframed as a style complaint) in the other
- [ ] I did not fix the known structural issue before running either review

## Reflection
Which version made it easier for a reviewer to tell you the layout itself was wrong, instead of commenting on how it looked? What does that suggest about showing polished mockups to stakeholders or teammates before structure is settled?
